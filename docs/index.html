Selective health data drive bias and unfairness in mortality prediction

Tutorials for the study. View the repository main page.

These guides show how to run the study primary pipeline and how to estimate participation weights using a cohort and one representative reference sample. Run all commands from the repository root. The repository README describes data access, software requirements, configuration, outputs and run times.

Synthetic inputs let you test the workflow without restricted data. Their results are not scientific estimates and cannot reproduce the paper's numbers. Reproducing the study requires approved access to the underlying data.

Before you start

Install the R packages listed in R_requirements.txt and the Python packages in requirements.txt. Point the pipeline to the Python interpreter containing those packages. On a machine without a CUDA GPU, set phase2.device to cpu in framework_config.json.

export REWEIGHTING_PYTHON=/path/to/python
export OPENBLAS_NUM_THREADS=1

Protect your inputs. bash data/regenerate_synthetic_inputs.sh overwrites files in the repository's data/ folders. Use it only in a fresh demonstration copy, never in a copy holding real data.

Each run prints its timestamped ID. Intermediate files are in temp/<run-id>/, reported outputs in results/<run-id>/, and the command manifest in temp/<run-id>/manifest/. To continue a run with a separate command, pass its ID with --run-id.

Tutorial 1: run the complete analysis

The pipeline has five phases: harmonise UKB, PMR, HSE and Census; measure prediction bias using UKB- and PMR-trained models; estimate participation weights; retrain UKB models with those weights and assess bias correction; and bootstrap the analysis for uncertainty intervals. PMR-trained predictions are out of fold. The unweighted bias analysis does not depend on the weighting phase.

1. Prepare demonstration inputs

In a fresh repository copy, generate the synthetic cohort, reference, geography and deprivation files:

bash data/regenerate_synthetic_inputs.sh

The generators reproduce the expected layout and variable types, but draw columns independently. Do not interpret the resulting mortality, bias or correction estimates.

2. Run the pipeline

Rscript run_pipeline.R --all

--all runs all five phases, including the bootstrap. With no selection option, the runner stops after phase 4 and reports point estimates only. Phase 5 takes longer because it refits the participation and outcome models for each configured replicate.

Alternatively, run phases separately. Start with phase 1, note the ID it prints, and use that ID for later phases:

Rscript run_pipeline.R --phase 1
Rscript run_pipeline.R --phase 2 --run-id <run-id>
Rscript run_pipeline.R --phase 3 --run-id <run-id>
Rscript run_pipeline.R --phase 4 --run-id <run-id>
Rscript run_pipeline.R --phase 5 --run-id <run-id>

Use --phase N --stage N for one stage, --from N to continue from a phase, or --jobs N to run independent fits concurrently. Later phases require earlier outputs in the same run.

Phase 1. Harmonisation

Harmonises the four sources onto shared coding schemes and applies the inclusion rules once to define the analytic populations. It also produces the record-flow table.

UKB is assembled by s1_harmonise_ukb.R through the recodes in _lib_ukb.R, PMR by s2_harmonise_pmr.R through _lib_pmr.R, and the two reference samples by s3_harmonise_hse.R and s4_harmonise_census.R. The coding scheme all four map onto is declared once in _lib_shared.R, and the public geography lookups are read in _lib_geography.R. Every inclusion rule is declared in _lib_rows.R and applied in one place by s5_build_population.R. The record flow is written by s6_flow_table.R.

Phase 2. Prediction bias

Trains separate UKB and PMR outcome models, evaluates both on PMR, and compares predicted with observed mortality. PMR predictions are held out by fold; UKB training is separate from the evaluation population.

The folds are fixed first by s1_assign_folds.py and the models trained by s2_train.py, whose survival components, the weighted Cox partial likelihood, the weighted Breslow baseline hazard and the construction of the outcomes, are in survival.py. Predictions are collected by s3_assemble.py, turned into cumulative incidence by s4_cumulative_incidence.py and reported by s5_results.py, with the strata and plotting helpers in reporting.py.

Phase 3. Participation weighting

Estimates the participation weights selected in framework_config.json and reports their diagnostics. Tutorial 2 gives a weights-only example, and names the script behind each method.

Phase 4. Bias correction

Retrains the UKB outcome models using the selected weights and measures how much of the prediction gap is reduced.

The weighted source is trained, assembled and turned into cumulative incidence by the same three scripts phase 2 uses, so the correction differs from the bias in the training weights and in nothing else. The correction is reported by s1_results.py.

Phase 5. Uncertainty

Uses multiplier-bootstrap replicates that refit the participation and outcome models to produce percentile intervals for bias and correction.

Each replicate draws its multipliers in multiplier_bootstrap.py, is run end to end by s1_replicates.sh and reduced to one rates table by replicate_rates.py. The intervals are formed by s2_intervals.py. On the synthetic inputs one replicate is one participation model and 42 outcome fits, which takes 85 seconds with the reported method, so ten replicates take about 14 minutes and the ten configured in framework_config.json for a demonstration are far fewer than the 200 the study reports. Set the count to match the interval level: at 0.95 each tail needs 80 replicates, and below that the bounds are the extreme replicates rather than estimated quantiles, which the stage warns about.

Check results

The figures and tables are in results/<run-id>/, organised by phase; the README names each output. Phase 1 reports the record flow, phase 2 unweighted bias, phase 3 weights and diagnostics, phase 4 weighted correction, and phase 5 bootstrap intervals. The manifest records commands, exit status, runtime and computing environment. Keep it with the outputs when documenting a rerun.

For an approved real-data run, place inputs in the layouts described in the README and use the same commands. Do not run the synthetic generator after placing real inputs there. The analysis settings are in framework_config.json.

Tutorial 2: estimate participation weights

This shorter workflow is for researchers holding a cohort and one representative reference sample. It harmonises shared variables, fixes the analytic cohort and estimates weights without PMR outcomes or the other reference sample. The example uses UKB and HSE. A single-reference run may retain more cohort records than the full study, which applies inclusion rules across all data pipelines.

Step 1. Choose the method

Set phase3.weight_method in framework_config.json. The default, hse_superlearner, is the primary method. Alternatives are hse_lassologit, hse_raking, hse_entropy_balancing and census_superlearner. They differ in cost as well as in method, because each bootstrap replicate re-estimates the participation model: end to end at ten replicates on the synthetic inputs, raking takes 4.4 minutes, entropy balancing 5.5, the Census Super Learner 15.2, the HSE Super Learner 16.2 and the lasso-penalised logistic regression 49.6. Choose an HSE method for the commands below; for the Census method, use --pipelines census.

Super Learner and lasso estimate UKB-membership probabilities out of sample and convert them to inverse-odds weights. Raking and entropy balancing directly match reference margins without fitting a membership model. Model-based weights are winsorised at the configured percentiles when used downstream; clipping moment-matched weights would undo their constraints. If a moment-matching solver warns that it has not reached its balance tolerance, inspect its diagnostics before using those weights.

Step 2. Generate demonstration inputs and harmonise

For a synthetic demonstration in a fresh copy, generate the inputs and run phase 1 for HSE. Note the printed run ID:

bash data/regenerate_synthetic_inputs.sh
Rscript run_pipeline.R --phase 1 --pipelines hse

For real data, omit the generator and provide cohort, HSE, geography and deprivation files in their documented locations. HSE survey weights are used when fitting the participation model.

Step 3. Estimate weights and diagnostics

Rscript run_pipeline.R --phase 3 --run-id <run-id> --pipelines hse

For Super Learner, inner five-fold cross-validation learns how to combine base learners; five outer folds give each record one held-out participation probability. Phase 3 checks that the weight file covers the analytic cohort and reports model performance where applicable, weight distribution, effective sample size and overlap.

The HSE methods are produced by s1_estimate_hse.R, which stacks the two samples and fits the participation model in _lib_hse.R, with the learner library and the cross-fitting regime in _lib_superlearner.R. The Census method is produced by s2_estimate_census.R through _lib_census.R, and raking and entropy balancing by s3_moment_weights.R, solved in _lib_moment.R. The variables shared between the cohort and the survey are harmonised in phase 1, in _lib_hse.R, and the auxiliary sets are declared under phase1.predictors. The diagnostics are written by s4_diagnostics.R and drawn by s5_results.py.

The cohort weight file is temp/<run-id>/weights/<method>/ukb_weights.csv. For model-based methods, it contains held-out participation probabilities and normalised inverse-odds weights before winsorisation. The outcome-model code applies the configured winsorisation when it reads them; the original file remains unchanged. Moment-matched weights are not winsorised and have no participation probabilities.

The reported diagnostics are in results/<run-id>/phase3_weighting/: weight_summary.xlsx and weight_distribution.png. Model-based methods also produce weight_positivity.xlsx and weight_overlap.png; these probability-based overlap outputs are not applicable to raking or entropy balancing. Values from the synthetic demonstration confirm only that the workflow runs.
